# Pragmatic DDD Skills 使用说明

> 面向使用者。想知道「我现在该做什么、说句话会触发什么」，看这一份。
> 想知道每个 Skill 内部怎么实现，看各自的 `SKILL.md`；想查规范，看知识包 `kb/`（`kb/README.md` 是路由表）。

## 0. 先建立一张地图

```
需求
 ↓  ddd-design-doc（一轮）
业务语义-V01 → 写聚合-V01 → 读投影-V01
 ↓  S2 → S3 → S4 / S6
代码落地 → 核对三条 → 冻结
 ↓  下次调整
业务语义-V02 → 写聚合-V02 → 读投影-V02 …
```

- **一轮三件套**：文件名带 `-V{NN}`，不覆盖；不适用就薄写，不省略、不跳号。
- **落地即冻结**：代码落地后三份不再改；设计要变开下一轮（`-V02`）。人判断换了业务目标，才新建需求目录。
- **现状看代码**：每轮按固定勘察清单现读，不产现状文档。

## 1. 我现在的情况 → 用哪个

| 你的情况 | 用什么 | 你会拿到 |
| --- | --- | --- |
| 刚接触，想建个 DDD 工程 | S1 `ddd-project-init` | pom、四层目录、配置模板、**前置条件清单空模板** |
| 有需求，还没想清聚合怎么划 | P2 `ddd-modeling-guide` | 只对话引导，不出文件 |
| 有需求，要出设计文档 | `ddd-design-doc` | 三件套（语义需你先确认） |
| 想知道某个聚合现在实际是什么 | `ddd-design-doc`（说「现在是实际什么」） | 按勘察清单读代码直接回答（不产文档） |
| 有设计文档，要建目录 | S2 `ddd-aggregate-scaffold` | 空目录骨架 |
| 要配数据库 / 总线 / ES / Redis | S3 `ddd-infra-config` | 配置类 + 建表 SQL |
| 有设计文档，要生成聚合代码 | S4 `ddd-aggregate-create` | 聚合根、注册表、规则、事件、应用层 |
| 已有聚合，要加动作 / 规则 / 订阅 | S5 `ddd-aggregate-extend` | 增量改动 |
| 有投影设计，要生成读模型 | S6 `ddd-projection-create` | 投影 DTO、源、裁剪器、读服务 |
| 有代码，要查合规 | S7 `ddd-code-review` | 阻断项 + 建议项 |
| 只想问规范为什么这么定 | `ddd-kb-consult` | 带出处的解释 |

## 2. 一轮的三件套（+ 一份跨轮的判决名单）

| 文档 | 回答什么 | 谁写 | 谁看 | 结束方式 |
| --- | --- | --- | --- | --- |
| ① 业务语义 | 本轮它应该是什么 | 设计文档 Skill 起草，**你确认** | 业务方、开发 | 落地后冻结 |
| ② 写聚合 | 本轮怎么写 | 设计文档 Skill | 开发 | 落地后冻结 |
| ③ 读投影 | 本轮怎么查 | 设计文档 Skill | 开发 | 落地后冻结 |
| ④ 判决名单 | 哪些事已经定了（跨需求累积） | 设计文档 Skill 追加，**你拍板** | 后来接手的会话 / 人 | **只增不改，永不归档** |

一句话记法：**三份是这轮约好了什么；④ 是历史上定了什么；现在实际是什么——看代码。**

④ 不记代码状态（字段 / 表 / 操作码一律不写），只记人的判决；已定过的不重议。详见 `kb/bp/design-doc-accepted.md`。

**落盘位置**

| 文档 | 路径 |
| --- | --- |
| 三件套 | `docs/design/changes/active/{需求}/{agg}/` 下的 `semantics-V{NN}.md` / `aggregate-design-V{NN}.md` / `projection-read-V{NN}.md`；需求交付后整目录移到 `changes/archive/{需求}/{agg}/` |
| ④ 判决名单 | `docs/design/aggregates/{agg}/accepted.md`（一聚合一份，**不随需求归档搬走**）；目录由 `design-doc-workspace.sh init / new` 预置，文件由 Skill 首次创建 |
| 轮次 | `V{NN}` 两位补零、每聚合目录内独立递增；几个聚合几个目录 |
| 前置条件清单 | `docs/design/prerequisites.md`（项目级，一份） |

目录操作可直接用脚本：`scripts/design-doc-workspace.sh init|new|next-round|archive|list`（脚本随能力包提供，不落盘到目标工程）。落点按「显式 `DESIGN_ROOT` → 当前 git 仓库根 → 当前工作目录」解析，固定为 `<根>/docs/design`，在目标工程里执行即无需传参。`next-round` 算下一个 V 号并列出该建的三份文件；归档时 `archive` 支持 `--yes` 跳过人工确认——AI / CI 等无 TTY 场景必须带，否则会取消归档。

## 3. 五个典型场景

**场景一：全新项目**

1. S1 初始化 → 顺手把前置条件清单里能定的先定了。
2. `ddd-design-doc` 出三件套（`V01`，头部写「基线：无（新建）」）。
3. S2 建目录 → S3 配基础设施 → S4 生成聚合 → S6 生成投影。
4. S7 评审 → 落地核对三条 → 三份置「已落地」→ 冻结。

**场景二：存量项目第一次用**

存量项目没有契约基线，直接写 ① 会失去基线。正确顺序：

1. 先让 `ddd-design-doc` 按**固定勘察清单**读代码（说「梳理一下 Order 现在的实际情况」），直接得到现状。
2. 只对本轮要改的聚合开 `V01` 写三件套，其余聚合等有需求时再说。
3. 之后按场景三走。

**场景三：常规迭代**

1. 按勘察清单读代码，摸清当前态；若上一轮已落地，用 `next-round` 算新轮次号；顺带读 `accepted.md`，命中旧判决不重议。
2. `ddd-design-doc` 出 `semantics-V0N`（只写受影响章节，差异就地标「（当前：…）」）。
3. 你确认语义 → 出 `aggregate-design-V0N` 与 `projection-read-V0N`（不适用就薄写）。
4. 实施 → 落地核对三条 → 填 §10.6 实施备注 → 三份置「已落地」→ 有新判决则追加进 ④ → 冻结。

**场景四：给已有聚合加能力**

1. `ddd-design-doc` 出 ① 的增量 + ② 的 §8 改动清单。
2. S5 按 ② §8 逐条改，不重写整聚合。

**场景五：紧急修复**

不走全流程。直接修代码，然后：

1. 下轮开场按勘察清单重新读代码即可——**不需要先补任何文档**。
2. 若这次修的是设计里写错的东西，那其实是设计变更：开下一轮，不在已落地的那份里改。

线上着火时不写契约，事后也不靠补文档找基线——**基线永远是代码**。

## 4. 三种强度，不用每次都全量

| 档 | 什么时候用 | 产出 |
| --- | --- | --- |
| 轻 | 改一个字段口径、调一条规则 | 三件套，其中 ②③ 可薄写 |
| 中 | 常规迭代（加动作、加校验、加查询） | 三件套 |
| 重 | 新聚合、大改、涉及表结构 + 投影 | 三件套，内容更厚 |

判断依据是**影响面**，不是工作量预估。无论哪档，三份都要在（薄写也算在）。

## 6. 什么情况下会被要求补文档

这是**设计如此**，不是 Skill 不听话：

| 你说 | Skill 会 | 原因 |
| --- | --- | --- |
| 「直接帮我生成订单聚合」 | 先要 ② 写聚合设计文档 | 生成阶段不自己编语义，否则等于重新设计一遍 |
| 「生成订单的查询接口」 | 先要 ③ 读投影设计文档 | 读模型的三族、副本、裁剪都得先定 |
| 「配一下 ES」 | 先要前置条件清单 | ES 版本、是否开安全未知，配了也连不上 |

如果确实想跳过，可以明确说「先不按流程，我自己负责」——但产物不会有设计基线，后续只能靠读代码重建。

## 7. 开始前你要准备什么

| 准备 | 什么时候要 | 没有会怎样 |
| --- | --- | --- |
| **前置条件清单** | 出设计文档、配基础设施、生成代码 | 数据库 / 总线 / Outbox 只能靠猜 |
| 业务需求或 PRD | 出 `semantics-V0N` | 无输入 |
| 代码基线（存量项目） | 现状梳理 | 读代码即可，但结论不落文档 |
| 设计文档（②③） | 生成代码 | 会被要求先补 |

前置条件清单在 S1 初始化时会生成空模板，10 项全部「待确认」，不预填默认值。

## 8. 四个常见误区

| 误区 | 后果 | 正确做法 |
| --- | --- | --- |
| 把 ① 写成需求的复述 | 只有「要什么」，没有「应该是什么」，设计阶段无从推导 | ① 每条都要有业务口径判断 |
| 把现状抄成一份文档 | 抄的那一刻就开始腐化，下次还得核验，等于白做 | 现状只现场读代码，不落文档 |
| 落地后还想改已冻结的那份 | 历史凭证被改，上一轮与下一轮口径对不上 | 设计要改开下一轮 `V{N+1}` |
| 凭感觉判断开新目录还是新轮 | 目录切错会断开收敛链条 | 拿不准先问用户，别自己定 |
