# Pragmatic DDD Skills 使用说明

> 面向使用者。想知道「我现在该做什么、说句话会触发什么」，看这一份。
> 想知道每个 Skill 内部怎么实现，看各自的 `SKILL.md`；想查规范，看 `../documentation/best-practices/`。

## 0. 先建立一张地图

```
需求
 ↓  ddd-design-doc
① 本次需求语义 → ② 聚合写设计 → ③ 投影读设计
 ↓  S2 → S3 → S4 / S6
代码
 ↓  S7 评审
④ 聚合事实（从代码推导，永续）
```

- **①②③ 是契约**：每需求一份，做完就归档。
- **④ 是快照**：只有一份，从代码推导，每次实施后覆盖。
- 下次需求从 ④ 起步，不从旧设计文档起步。

## 1. 我现在的情况 → 用哪个

| 你的情况 | 用什么 | 你会拿到 |
| --- | --- | --- |
| 刚接触，想建个 DDD 工程 | S1 `ddd-project-init` | pom、四层目录、配置模板、**前置条件清单空模板** |
| 有需求，还没想清聚合怎么划 | P2 `ddd-modeling-guide` | 只对话引导，不出文件 |
| 有需求，要出设计文档 | `ddd-design-doc` | ①②③（语义需你先确认） |
| 想知道某个聚合现在实际是什么 | `ddd-design-doc`（说「现在是实际什么」） | ④ 事实文档 |
| 有设计文档，要建目录 | S2 `ddd-aggregate-scaffold` | 空目录骨架 |
| 要配数据库 / 总线 / ES / Redis | S3 `ddd-infra-config` | 配置类 + 建表 SQL |
| 有设计文档，要生成聚合代码 | S4 `ddd-aggregate-create` | 聚合根、注册表、规则、事件、应用层 |
| 已有聚合，要加动作 / 规则 / 订阅 | S5 `ddd-aggregate-extend` | 增量改动 |
| 有投影设计，要生成读模型 | S6 `ddd-projection-create` | 投影 DTO、源、裁剪器、读服务 |
| 有代码，要查合规 | S7 `ddd-code-review` | 阻断项 + 建议项 |
| 只想问规范为什么这么定 | `ddd-kb-consult` | 带出处的解释 |

## 2. 四份文档的分工

| 文档 | 回答什么 | 谁写 | 谁看 | 结束方式 |
| --- | --- | --- | --- | --- |
| ① 本次需求语义 | 这次它应该是什么 | 设计文档 Skill 起草，**你确认** | 业务方、开发 | 验收后归档 |
| ② 聚合写设计 | 这次怎么实现 | 设计文档 Skill | 开发 | 实施后归档 |
| ③ 投影读设计 | 这次怎么查 | 设计文档 Skill | 开发 | 与②同批归档 |
| ④ 聚合事实 | 现在实际是什么 | 从代码推导 | 所有人 | **永不归档** |

一句话记法：**①②③ 是这次答应了什么，④ 是现在实际是什么。**

**落盘位置**

| 文档 | 路径 |
| --- | --- |
| ①②③ | `docs/design/changes/active/{需求}/{agg}/`（`semantics.md` / `aggregate-design.md` / `projection-read.md`），归档时整目录移到 `changes/archive/{需求}/{agg}/` |
| ④ | `docs/design/aggregates/{agg}/facts.md`（一个聚合一份，永不归档） |
| 前置条件清单 | `docs/design/prerequisites.md`（项目级，一份） |

目录操作可直接用脚本：`scripts/design-doc-workspace.sh init|new|archive|list`（脚本随能力包提供，不落盘到目标工程）。

## 3. 五个典型场景

**场景一：全新项目**

1. S1 初始化 → 顺手把前置条件清单里能定的先定了。
2. `ddd-design-doc` 出 ①②③（① 头部写「基线：无（新建）」）。
3. S2 建目录 → S3 配基础设施 → S4 生成聚合 → S6 生成投影。
4. S7 评审 → 更新 ④。

**场景二：存量项目第一次用**

存量项目没有 ④，直接写 ① 会失去基线。正确顺序：

1. 先让 `ddd-design-doc` 产出 ④（说「梳理一下 Order 现在的实际情况」）。
2. 只对**本次要改的聚合**补 ①，其余聚合等有需求时再说。
3. 之后按场景三走。

**场景三：常规迭代**

1. 读 ④ 当前态。
2. `ddd-design-doc` 出 ①（只写受影响章节，差异就地标「（当前：…）」）。
3. 你确认 ① → 出 ②③（新版 `v{N+1}`）。
4. 实施 → 填 ② 的 §10.6 → **更新 ④** → ①②③ 归档。

**场景四：给已有聚合加能力**

1. `ddd-design-doc` 出 ① 的增量 + ② 的 §8 改动清单。
2. S5 按 ② §8 逐条改，不重写整聚合。

**场景五：紧急修复**

不走全流程。直接修代码，然后：

1. ④ 里删掉对应的问题行（如果修的就是它）。
2. ④ §5 变更记录加一行。

线上着火时不写契约，但**④ 必须补**——否则下次需求从错的基线起步。

## 4. 三种强度，不用每次都全量

| 档 | 什么时候用 | 产出 |
| --- | --- | --- |
| 轻 | 改一个字段口径、调一条规则 | 更新 ④ + ① 只写受影响的一两章 |
| 中 | 常规迭代（加动作、加校验、加查询） | ④ + ① + ② |
| 重 | 新聚合、大改、涉及表结构 + 投影 | 四份齐 |

判断依据是**影响面**，不是工作量预估。

## 6. 什么情况下会被要求补文档

这是**设计如此**，不是 Skill 不听话：

| 你说 | Skill 会 | 原因 |
| --- | --- | --- |
| 「直接帮我生成订单聚合」 | 先要 ② 写设计文档 | 生成阶段不自己编语义，否则等于重新设计一遍 |
| 「生成订单的查询接口」 | 先要 ③ 投影读设计 | 读模型的三族、副本、裁剪都得先定 |
| 「配一下 ES」 | 先要前置条件清单 | ES 版本、是否开安全未知，配了也连不上 |

如果确实想跳过，可以明确说「先不按流程，我自己负责」——但产物不会有文档基线，④ 也无法更新。

## 7. 开始前你要准备什么

| 准备 | 什么时候要 | 没有会怎样 |
| --- | --- | --- |
| **前置条件清单** | 出设计文档、配基础设施、生成代码 | 数据库 / 总线 / Outbox 只能靠猜 |
| 业务需求或 PRD | 出 ① | 无输入 |
| 代码基线（存量项目） | 产 ④ | 无法推导当前态 |
| 设计文档（②③） | 生成代码 | 会被要求先补 |

前置条件清单在 S1 初始化时会生成空模板，10 项全部「待确认」，不预填默认值。

## 8. 四个常见误区

| 误区 | 后果 | 正确做法 |
| --- | --- | --- |
| 把 ① 写成需求的复述 | 只有「要什么」，没有「应该是什么」，设计阶段无从推导 | ① 每条都要有业务口径判断 |
| ④ 抄 ② 的内容 | ④ 是「当时打算怎么做」，不是「现在是什么」，一抄就失真 | ④ 的唯一来源是代码 |
| ①②③ 归档后还想改 | 破坏「历史凭证」的性质，评审失去依据 | 要改就出 `v{N+1}` |
| ④ 不更新就进下一次迭代 | 下次需求从错误基线起步，问题越滚越大 | ④ 是硬约束：不更新不进下一轮 |
