# BP 卡：聚合演进设计原则（aggregate-evolution-design）

> 源：`documentation/best-practices/aggregate-evolution-design.md` · 派生时间：2026-10-18 · 框架版本：2.0.0

## 1. 定位与适用场景

回答「既有聚合要改/加能力时，设计文档怎么写」。对应《聚合设计文档标准》「修改场景」，是 `ddd-design-doc` 在迭代需求下产出修改类文档的依据。全新需求走「聚合识别设计原则」。

| 场景 | 适用 |
| --- | --- |
| 加操作/命令 | 是（操作码声明 + 旧快照机制） |
| 加子实体/值对象 | 是（子表 vs 独立聚合判定） |
| 加领域事件/订阅 | 是（事件载荷 + 投影影响） |
| 演进式拆分 | 是 |
| 全新聚合 | 否 |

## 2. 根因分析三层（修改类必含）

| 层级 | 问什么 | 落点 |
| --- | --- | --- |
| 直接原因 | 哪段实现没拦住/没覆盖 | 具体代码（`行号:相对路径`） |
| 深层原因 | 为什么没拦住（执行顺序/模型漏洞） | 机制层面 |
| 本质原因 | 为什么会有这样的设计 | **职责/边界/模型层面**，非「忘了写判断」 |

## 3. 修改场景设计要点

- **加操作/命令**：操作码在 `operation-registry-design` 声明；前置类规则（如「仅待发货可发货」）必须读**旧快照** `old`（框架 `execute` 先跑领域逻辑后校验，当前态已改）。
- **加子实体/值对象**：随父存在无独立访问 → 同聚合子表（`TrackedList`+独立子表）；有独立访问/生命周期 → 提独立聚合；无身份值对象 → 并入父表 JSON 不建子表。
- **加事件/订阅**：事件载荷含改前/改后；订阅者与投影影响见 `event-subscriber-pattern`/`projection-design`；即便零改动投影也写「零改动，理由：……」。

## 4. 改动清单与落地顺序

按《聚合设计文档标准》§11：表格三列（确切文件路径 + 动作新增/改/删 + 说明）；另给落地顺序保证每步可编译可单测（如先立规则与操作码，再改聚合，最后接应用层与接口层）。

## 5. 版本化

迭代文档一版一版：`vN`，顶部结论先行块标注**版本 vN** + 「替代 v(N-1) 的哪些章节」；文件名 `{聚合名}-aggregate-design-v{N}.md`；多轮文档串成版本链。

## 6. 范围控制

顺带发现的同类缺口一律记风险表标「**不在本次范围**」另开文档，避免范围蔓延。设计文档只引框架机制链接不重复讲。

## 7. 常见反模式

| 反模式 | 正确做法 |
| --- | --- |
| 只有方案没根因 | 写三层根因，本质落职责/边界 |
| 状态前置规则读当前态 | 前置判断必须读 `old` |
| 只正文描述改动无清单表 | 独立改动清单表+落地顺序 |
| 期望写「报错/失败」 | 写确切消息码常量名与状态枚举值 |
| 顺手一起改顺带缺陷 | 记风险表标「不在本次范围」 |
