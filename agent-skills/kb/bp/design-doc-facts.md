# BP 卡：聚合事实文档模板（实现快照）

> 源：`documentation/best-practices/design-doc-facts.md` · 派生时间：2026-10-29 · 框架版本：2.1.0-SNAPSHOT

## 1. 定位

四份文档里唯一的**快照**，也是唯一长期维护的一份。三份契约回答「这次答应了什么」，本卡回答「现在实际是什么」。

| 文档 | 性质 | 份数 | 结束方式 |
| --- | --- | --- | --- |
| 本次需求语义（`bp.design-doc-semantics`） | 契约 | 每需求一份 | 验收后归档 |
| 聚合写设计（`bp.design-doc-write-template`） | 契约 | 每需求一份 | 实施后归档 |
| 投影读设计（`bp.design-doc-read-template`） | 契约 | 每需求一份 | 与写同批归档 |
| **聚合事实（本卡）** | **快照** | **1 份** | **永不归档** |

落盘：`docs/design/aggregates/{agg}/facts.md`。

## 2. 更新机制

| 项 | 约定 |
| --- | --- |
| 触发 | 每次实施完成 |
| 输入 | 代码（主）+ 写设计 §10.6 回填（偏离） |
| 方式 | 覆盖更新，不追加历史版本；历史看变更记录 |
| 读者 | 下一次需求从这里读当前态，不从旧设计文档读 |
| 硬约束 | 未更新则下次迭代不得开始 |

## 3. 固定 5 节

| # | 章节 | 关键产物 |
| --- | --- | --- |
| 1 | 这份文档是什么 | 四份文档定位表 / 更新机制 / 与语义的分工 |
| 2 | 依据 | 核对日期、核对人、代码基线、来源设计文档 |
| 3 | 实际结构 | 字段 / 子实体 / 枚举 code / 表与索引（含表形态与 search 台账）/ 操作码 / 消息码 / 事件 / 规则挂载 |
| 4 | **未消除问题** | 问题 / 影响 / 来源 / 计划；不含「语义没写清」类事项 |
| 5 | 变更记录 + 生成方法 | 日期 / 来源设计 / 变更点 / 核对人；七步推导表 |

## 4. 关键硬约束

**只写实际**

- 不写「应该」、不写设计理由、不写未来方案。
- §4 只记**还没修**的问题，修掉就删行；完整比对（本次需求 vs 当前事实）写在语义文档对应章节，不在这里展开。
- 「语义没写清」类事项不入 §4（归语义文档）。

**已接受 / 已移交要显式列出**

- 已接受的现状：写在 §4 表后一段，避免被反复当成新问题。
- 已移交语义文档：列一句即可，便于下次写语义时接上。

**规则挂载表**

列：语义编号 / 消息码 / 组（A 全局、B 准入、C 状态前置）/ 激活条件 / 判定基准（变更前 old 或变更后）/ 读取字段。这张表是判断「语义说的规则是否真的挂上」的唯一依据。

## 5. 怎么生成（从代码推导）

本份**完全从代码推导**，不依赖语义文档：

| 步 | 读什么 | 产出 | 需判断 |
| --- | --- | --- | --- |
| 1 | 聚合根与子实体 | §3.1 / §3.2 | 否 |
| 2 | 枚举类 | §3.3 | 否 |
| 3 | DDL 与 Mapper 对照；`GENERATED ALWAYS AS` 与列形态 | §3.4 表与台账（A 展开列 / B JSON / search 生成列） | 是（不一致时以实际库为准） |
| 4 | 操作注册表 / 规则注册表 | §3.5 / §3.6 | 是（注册表外的方法要对照） |
| 5 | 事件类与订阅登记 | §3.7 | 否 |
| 6 | 规则容器 `addRule` 的 lambda | §3.8 | **是（读 `old` 还是当前态只能读 lambda 体）** |
| 7 | 代码 vs 已知问题 | §4 摘要 | 是（哪些算问题、是否已修） |

第 3、4、6 步含判断：第 6 步直接决定能不能发现「规则读错基准」这类问题，不能只看 `addRule` 签名就填表。
