# BP 卡：聚合业务语义文档模板（语义层）

> 源：`documentation/best-practices/design-doc-semantics.md` · 派生时间：2026-10-29 · 框架版本：2.1.0-SNAPSHOT

## 1. 定位

四份文档中的第一份契约：描述**本次需求**中这个聚合应该是什么。需求验收后归档。

| 文档 | 性质 | 份数 | 结束方式 |
| --- | --- | --- | --- |
| **本次需求语义（本卡）** | 契约 | 每需求一份 | 验收后归档 |
| 聚合写设计（`bp.design-doc-write-template`） | 契约 | 每需求一份 | 实施后归档 |
| 投影读设计（`bp.design-doc-read-template`） | 契约 | 每需求一份 | 与写同批归档 |
| 聚合事实（`bp.design-doc-facts`） | 快照 | 1 份 | 永不归档 |

落盘：`docs/design/changes/active/{需求}/{agg}/semantics.md`；归档随目录移到 `changes/archive/{需求}/{agg}/`。

### 1.1 增量写法（迭代需求）

不重写全量，只按章重列受影响的部分：

| 项 | 写法 |
| --- | --- |
| 头部基线 | `基线：aggregates/{agg}/facts.md（核对日 YYYY-MM-DD）` |
| 受影响章节 | 完整重列（含未变条目，保证单章可读） |
| 未受影响章节 | 写一行「无变更，见基线 §N」 |
| 新增 / 废弃 | 标「本次新增」/「本次废弃」并写原因 |
| 新建聚合 | 头部写「基线：无（新建）」，全量重列 |
| **与事实的差异** | **就地写在对应条目上**（`（当前：xxx）`），不另设差异章节 |

每章首行必须标本次处理方式，便于评审定位改了什么。

差异标注：写在本次要求与 ④ 不一致的那个属性 / 动作 / 规则 / 事件 / 状态行上；不写「怎么修」（归 ②），不重复 ④ 的完整现状。

## 2. 两种输入源

| 维度 | 现状型（从代码梳理） | 规划型（从 PRD 设计） |
| --- | --- | --- |
| 属性 / 动作 / 事件 / 规则 / 状态 | 代码字段、公开方法、事件收集点、规则容器、枚举 | PRD 业务对象、用例、异步通知、校验条款、状态定义 |
| 查询场景 | 现有查询入口 | 使用方提出的诉求 |
| 附录 C | 语义与实现偏差 | 需求缺口、待确认 |

规划型的要点：用户故事不是动作，要提炼；校验条款一句话一条、编号先分配；查询场景必须问出来，不能由设计者编造。

## 3. 固定目录（8 章 + 3 附录）

| # | 章节 | 关键产物 |
| --- | --- | --- |
| 1 | 聚合职责与边界 | 负责一段 + 不负责一段 |
| 2 | 聚合结构与属性 | 类图（关键字段）+ 聚合根属性 + 子实体属性 |
| 3 | 业务动作 | 动作清单 / 写入字段 / 重复执行语义 |
| 4 | 领域事件 | 事件清单（含载荷与消费方）/ 无人消费的事件 |
| 5 | 业务规则 | 全局不变量 / 动作专属 / 动作 × 规则矩阵 |
| 6 | 状态与流转 | 维度 / 流转过程 / 每维度一张图 / 动作 × 状态矩阵 |
| 7 | 外部依赖与协作边界 | 依赖谁 / 输入输出图 / 依赖失败后果 |
| 8 | 查询场景 | Q1…Qn：谁要查 / 查什么 / 用来做什么 / 业务筛选维度 |
| 附录 | A 术语口径 / B 场景走查 / C 与实现（或需求）的偏差 | |

## 4. 关键硬约束

**属性**

- 五列固定：属性 / 字段名（反引号）/ 业务含义 / 业务口径 / 谁能改（只填动作名）。
- 子实体必须有标识行，否则「改第 N 项」无所指；派生字段在口径列写出算式。

**动作**

- 3.1 只写状态变化，3.2 只写字段，两表边界不得混。
- 触发事件不允许留空，没有写「无」；重复执行语义每行都要能回答「连点两次会怎样」。

**事件**

- 载荷写字段名，不写「订单信息」这类笼统词；只带标识时明确写「仅 `entityId`」。
- 框架级数据同步事件也要列；无消费方的进 4.2 并写清后果。

**规则**

- R 编号全文稳定，分配后不重排、不复用。
- 每条规则必须标判定基准；**依赖被动作改掉的状态时必须按旧快照判定**，否则规则会恒失败。
- 「守的是什么」与规则同义就删掉，不单列成列。

**状态**

- 一维一行，不把每个取值拆行再重复维度名。
- 多维度必须显式声明「互不推导」并给证据句；每个维度一张图，不合并。
- 预留态必须标注并说明可达性。

**查询场景**

- 只写业务维度，不写查询形态（ById / 分页 / 滚动）、排序、分页大小、返回字段。
- 每条必须有「谁要查」与「用来做什么」；Q 编号全局唯一，下游逐条对应。

**表达形式**

- 图只表达结构与流转，清单与字段一律用表；图下不写「这张图说明……」。
- 同一事实只定义一次，其他章节引用编号。

## 5. 自检要点（14 项，摘要）

每属性至少一个动作能改 / 每动作有事件或写「无」/ 每规则至少一个触发动作 / 每状态取值可达或标预留 / 每事件有消费方或进 4.2 / 每依赖有失败后果 / 金额等式有守护 / 矩阵无空格 / 变更前规则依赖字段确实读不到 / R 编号无跳号 / 图不重复全量字段 / 术语覆盖全部名词 / 查询场景齐全且只写业务维度。
