# BP 卡：聚合设计文档标准（三件套 + 轮次 · 流程权威）

> 源：`documentation/best-practices/design-doc-template.md` · 派生时间：2026-11-01 · 框架版本：2.1.0-SNAPSHOT
> 本卡是**交付节奏与轮次规则的唯一权威**：一轮怎么走、怎么算落地、落地后能不能改、开新轮还是开新目录，只认这一份。

## 1. 三级结构与三件套

| 层级 | 单位 | 边界由谁定 |
| --- | --- | --- |
| 需求 | `changes/active/{需求}/` | 人：明确是新需求才新建 |
| 聚合 | `{需求}/{agg}/` | 涉及几个聚合就几个目录 |
| 轮次 | 文件名后缀 `-V{NN}`（`V01`…） | 每聚合目录内独立递增 |

| # | 文档 | 回答什么 | 落盘 | 结束方式 |
| --- | --- | --- | --- | --- |
| ① | 业务语义（`bp.design-doc-semantics`） | 本轮它应该是什么 | `semantics-V{NN}.md` | 落地后冻结 |
| ② | 写聚合（`bp.design-doc-write-template`） | 本轮怎么写，统管横切 | `aggregate-design-V{NN}.md` | 落地后冻结 |
| ③ | 读投影（`bp.design-doc-read-template`） | 本轮怎么查 | `projection-read-V{NN}.md` | 落地后冻结 |

- **每轮固定三份**：不适用时薄写「本轮无变更 + 原因 + 见 `xxx-V{M}.md` §N」，不省略、不跳号。
- **不覆盖写**：每轮各一份，旧轮次不删、不合并。
- **现状不在三件套里**：看代码，每轮按 §5.0 清单现读。

## 2. 编号与头部

`V{NN}` 是唯一对外编号；「第 N 稿」只在本轮内计数，不对外引用。

```text
轮次：V02 ｜ 第 2 稿 ｜ 状态：草稿 / 已确认 / 修订中 / 已落地 / 已归档
代码基线：abc123（核对 2026-11-05）
```

引用写 `semantics-V02.md §5`，不写「① v3」。

## 3. 一轮四阶段

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| 1 输入 + 勘察 | 解析需求；按 §5.0 清单读代码 | 无文档 |
| 2 出语义（G1 → G2） | ① 可多稿，用户显式说「定稿」才置「已确认」 | ① |
| 3 出技术设计 | ② + ③ 各一份，不跳过任一份 | ②③ |
| 4 落地 + 核对 | 交下游实施 → §5.3 核三条 → 置「已落地」 | 代码 |

- 语义未定稿不得动 ②③。
- **取消点单**：不再问「要不要出写设计 / 要不要出投影」。
- 纯技术轮也出 ①，只是薄写（一节说明「本轮无业务语义变更 + 影响面」）。

## 4. 回流（仅落地前）

判别式：**改的是「业务上说得通吗」→ 回 ①；改的是「技术上怎么落」→ 停在 ②③；两句话都沾 → 拆成两件事分别落。**

| 在哪发现 | 发现什么 | 回流到 |
| --- | --- | --- |
| ② | 规则 / 动作 / 事件载荷 / 状态维度 | ①（出新稿 → G2 → ② 对齐） |
| ② | 表结构 / 索引 / TypeHandler / 执行顺序 / 常量 | 止于 ②（§10.1） |
| ③ | 缺查询场景 Q | ①（§8，编号只增）→ ① 定稿 → ②（涉及字段时）→ ③ |
| ③ | 读源 / mapping / `REPLICA_ID` / TTL / 分页 / 索引 | 止于 ③ |
| 任意 | 与代码实际不一致 | ① 就地标 `（当前：xxx）`，不擅自抹平 |

- **不跳级**：顺序固定 `① 定稿 → ② 对齐 → ③ 对齐`。
- **落地后不再回流**：缺陷型问题改代码；设计要变开下一轮。

## 5. 落地 / 冻结 / 归档

### 5.1 代码勘察清单（每轮开场，不产出文档）

聚合根与子实体 / 枚举 code / 操作码与消息码 / 规则容器 `addRule` 的 lambda（**读 `old` 还是当前态只能看 lambda 体**）/ DDL + Mapper（含列形态与 TypeHandler）/ 事件与订阅登记。

### 5.2 落地核对（一轮结束的判据）

| # | 核对项 | 依据 |
| --- | --- | --- |
| 1 | 改动清单逐行有实现 | ② §8 |
| 2 | 操作码与规则逐列一致（消息码 / 组 / 激活条件 / 读取字段） | ② §3.1 / §4.4 |
| 3 | 查询族与读服务有实现、能编译 | ③ §6 |

三条全过 → 置「已落地」，本轮结束。任一不过 → 改代码，或落地前改设计；**不许带着不一致宣布落地**。

### 5.3 冻结与两个例外

| 例外 | 范围 |
| --- | --- |
| 文字勘误 | 错别字、失效链接、格式、编号笔误（不改结论） |
| 实施备注 | ② §10.6：设计未细化处的实施事实（签名核实、方言细节、装配细节） |

设计内容（规则 / 字段 / 动作 / 事件 / 状态 / 表结构 / 查询）要变 → 开下一轮。

### 5.4 归档

需求交付后整目录搬到 `changes/archive/{需求}/`，各轮文件一起走。归档判据：§5.2 三条已过。

## 6. 一致性校验（落地前）

1. ① 的 R / 动作 / 事件 / 状态维度 ⊆ ② §1.4，且 ② 无 ① 没有的动作。
2. ③ 的 Q 集合 = ① §8（不多不少、编号不改）。
3. ③ §1.2 来源事件 ⊆ ② §5.1。
4. ③ §3.1 投影字段 ⊆ ② §7（枚举已降级）。
5. 三件套齐全；薄写的已写清「无变更 + 原因 + 指向上一轮」；三份不为「待对齐」。

## 7. 轮次判定（开新轮还是开新目录）

默认：**能推出来就加后缀，推不出来就建新目录。** 三条全满足才加 `-V{N+1}`：

1. 业务目标相同（同一批对象、同一件事的延续）；
2. 上一轮三件套在同目录且能作基线；
3. 能写出「本轮替代上一轮什么」（哪几条 R / 哪个动作 / 哪个查询）。

任一含糊 → 新建需求目录；**拿不准必须问用户**，禁止自行择一。

## 8. 被读于

`ddd-design-doc`（轮次、落地、冻结、回流、校验的执行依据）、`ddd-kb-consult`（文档节奏咨询）、S3–S7（取当前有效文档：glob 该类型 + 取最大 V）。
