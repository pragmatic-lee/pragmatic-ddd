# BP 卡：聚合数据库设计原则（aggregate-database-design）

> 源：`documentation/best-practices/aggregate-database-design.md` · 派生时间：2026-10-29（两层判定 / A·B 形态同步） · 框架版本：2.1.0-SNAPSHOT

## 1. 核心原则：表边界 = 聚合边界

一个聚合对应**一组表**：聚合根一张主表，有独立身份的实体各自成子表。判定分两层：**第一层**集合怎么落表（§2），**第二层**值对象怎么落列（§3）。

```text
Order 聚合
├─ t_order          基础列 + 金额展开列（A） + Customer/Address JSON（B） + search_* 生成列 + version
└─ t_order_item     子实体表（OrderItem，独立 id，TrackedList 差量）
```

不跨聚合建物理外键：聚合间只持 ID，一致性由应用层 + 单聚合事务保证。

## 2. 第一层：集合怎么落表

| 子对象形态 | 表设计 |
| --- | --- |
| 有独立 ID、独立行、随聚合增删的实体 | 独立子表 + `TrackedList` 差量 |
| 可能被其他聚合独立访问的「子实体」 | 不是子表，是独立聚合 |
| 无身份内嵌值对象 | 父表一列（JSON 或展开，见 §3） |
| 无身份值对象集合 | 单列 JSON 数组（`ListTypeHandler`） |

「多」的定法：聚合根一张主表 + 每个有独立身份实体一张子表；一个实体只归属一个聚合、只一张表。

## 3. 第二层：值对象落列（形态 A / B）

**选择粒度是值对象**：同表可混用，同一值对象只能选一种（不允许 JSON + 同义展开列双存）。**默认 B，A 需准入。**

| 项 | 形态 A 展开平铺 | 形态 B JSON + 派生列 |
| --- | --- | --- |
| 写权威 | 列 | JSON |
| 查询列 | 列本身 | `search_*` 生成列（**只许生成列**） |
| 加字段 | DDL 迁移 | 零 DDL |
| 改结构 | DDL 迁移 | 数据迁移 |
| DB 约束 | 原生 | 生成列 + 唯一索引 |
| BI 直连 | 友好 | 需视图 |

**A 的四条硬规则**

1. 同一值对象全部列在**同一条** INSERT/UPDATE 写全（否则并发下半个值对象）；
2. resultMap 用嵌套属性映射（`totalAmount.amount`），领域层不感知列；
3. 可空性与 DDL 对齐（不可空 → `NOT NULL`）；
4. 不得再给该值对象建同义生成列。

**B 的五条硬规则**

1. JSON 是唯一写入口，值对象整体替换；
2. `search_*` **只能是生成列**，应用不写；
3. 生成列不进领域模型、不进 INSERT/UPDATE、不用 `SELECT *`；
4. 每个生成列必须建索引，每表 ≤ 5（索引预算）；
5. 生成列只能做**单行内、确定性**推导。

**判据（满足任一才用 A）**：值对象全部字段都是查询/约束依据；结构极稳定（`Money`/`GeoPoint`）；需要数据库级约束；外部系统必须直连平表且不许加视图。其余一律 B。

**生成列解决不了（转读侧）**：跨行汇总（G1）、外部数据/字典翻译（G2）、全文分词（G3）、JSON 数组包含（G4）。枚举 name 不用 `CASE` 生成列（改用读侧回填）；时区统一 UTC 存。

**迁移**：A↔B 都是数据迁移，没有免费通道 → 形态必须在设计期定。

**台账**：形态无法从表结构反推，必须在 `design-doc-facts` 登记「表形态 + search 列（path → 列 → 精度 → 索引）」。

## 4. 合理性三问

一致性（同一事务）/ 边界（子实体不外泄）/ 读写（JSON 查不动或 join 太重）。三问全过才算合理；另加**形态复核**：每个值对象已按 §3 选定 A/B 并登记台账。

## 5. 表结构规范

- 主键：聚合根表 = `entityId`（非自增）；子实体表 = 自身 `id`，`order_id` 作逻辑外键（过滤键），不入领域、不映射。
- 映射：值对象默认 JSON；A 型用嵌套属性映射；派生列只读。
- 审计列：`created_at/by`、`updated_at/by` 由父类托管，必须预留。
- 版本列：主表必须有 `version`（乐观锁 CAS），子表不设。
- 业务唯一号与 `entity_id` 不同时，单独成列 + 唯一索引，不塞 JSON。

## 6. 一致性策略

无物理外键（应用事务 + 先子后主）；`version` CAS 冲突抛 `OptimisticLockingFailureException`；子集合 `TrackedList` 只发增量。

## 7. 常见反模式

| 反模式 | 正确做法 |
| --- | --- |
| 为无身份值对象建子表 | 并入父表一列 |
| 把有独立身份的实体塞进 JSON | 独立子表 + `TrackedList` |
| 跨聚合建物理外键 | 只保留 ID 引用 |
| 一个实体多表重复存储 | 一个实体只归一个聚合、一张表 |
| 子表不加逻辑外键索引 | `order_id` 建普通索引 |
| 主表缺 `version` / 审计列 | 预留版本列与四审计列 |
| 逻辑外键映射进子实体 | 不入领域、不入 resultMap |
| 同一值对象既 JSON 又手写展开列 | 一个值对象只选一种形态 |
| 自建 `search_*`（应用写） | `search_*` 只能是生成列 |
| 生成列进 INSERT/UPDATE 或被映射进聚合 | 生成列只读、只给查询侧 |
| 建了 `search_*` 不建索引 | 每个生成列配一个索引 |
| 展开写值对象只更新部分列 | 全列同一条语句写全 |
| 用生成列做跨行汇总/字典/分词 | 转读侧：视图 / 直读 / ES / FULLTEXT / GIN |
| `search_*` 放手机号等敏感字段 | 敏感字段不进派生列 |
