# BP 卡：聚合识别设计原则（aggregate-identification）

> 源：`documentation/best-practices/aggregate-identification.md` · 派生时间：2026-10-18 · 框架版本：2.0.0

## 1. 定位与适用场景

战略建模步骤：回答「一份需求怎么识别出应该有哪些聚合」。既用于全新需求从 0 识别，也用于迭代中「要不要新增聚合」的判断。识别结果喂给 `aggregate-design`，最终落为符合《聚合设计文档标准》的文档。

| 场景 | 适用 |
| --- | --- |
| 全新需求 | 是，从需求识别聚合候选+边界 |
| 迭代（加聚合） | 是，判扩既有还是独立新聚合 |
| 迭代（改聚合） | 否，边界已定走「聚合演进设计」 |

识别阶段**不写代码、不出设计文档正文**，只产出「聚合候选清单 + 边界 + 不变量 + 粒度结论」。

## 2. 识别四步（事件风暴）

1. **列事件**：引导列业务事件（过去式、事实语义）；每事件归属潜在聚合；同动作下事件密集且需**强一致**的归同一聚合候选。
2. **提炼不变性**：对每个候选追问「哪些规则必须在**一次事务内**保持一致」；强一致（订单总额=Σ项金额）→ 同聚合；最终一致（支付成功→扣库存）→ 跨聚合走事件。
3. **定边界**：强一致（A 不变性依赖 B 当前态、同事务）→ A、B 同聚合；最终一致（A 只关心 B「发生了什么」）→ 跨聚合，B 发事件 A 订阅。
4. **定粒度（小聚合原则）**：是否引入不需一起加锁的实体（是→拆出）；跨聚合是否只持 ID；子实体是否随父存在无独立访问（是→同聚合子表；否→独立聚合）。

## 3. 边界判据清单

识别完成应明确：①聚合根是谁+为什么 ②含哪些实体/值对象 ③**不归本聚合管什么**（防蔓延）④维护哪些核心不变量 ⑤与其他聚合强一致还是最终一致。缺一则回 §2。

## 4. 迭代「加聚合」判定

1. 新能力不变量与某既有聚合同事务强一致？→ 扩到该聚合（走演进设计）。
2. 否则有独立生命周期/独立访问？→ **新增独立聚合**。
3. 仅是既有聚合新只读视图 → 走投影读模型，不增聚合。
经验法则：加进既有聚合会膨胀、并发冲突上升 → 倾向独立成聚合，跨聚合以事件/ID 协作。

## 5. 常见误判与反模式

| 误判 | 纠偏 |
| --- | --- |
| 一个聚合包下整个领域 | 按不变性切小聚合 |
| 跨聚合持对象引用 | 只持 ID（约束 13） |
| 最终一致当强一致硬塞 | 跨聚合走领域事件 |
| 无身份值对象建独立子表 | 并入父表 JSON |
| 子实体被他聚合独立访问却塞同聚合 | 提为独立聚合 |
