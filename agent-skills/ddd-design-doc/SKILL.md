# ddd-design-doc（聚合设计文档产出）

> 类型：设计文档产出能力
> 版本：v4.0 · 适用框架：2.1.0
> 共享知识：`../kb/`（只读引用，见 `../kb/README.md`）
> 统一结构：`documentation/best-practices/design-doc-template.md`（三件套 + 轮次总说明）+ 三份模板
> 模板形态：设计文档模板随能力包提供（只读引用，**不写入目标工程**）；目标工程只产出 `docs/design/` 下设计文档，不新建任何模板文件。

## 1. 定位

把「一份需求」转化为**一个轮次的三件套**。**现状不落文档，一律以代码为准**：

| 文档 | 回答什么 | 落盘 | 结束方式 |
| --- | --- | --- | --- |
| ① 业务语义 | 本轮这个聚合应该是什么 | `changes/active/{需求}/{agg}/semantics-V{NN}.md` | 落地后冻结 |
| ② 写聚合 | 本轮怎么写（模型 + 关系表），统管横切 | 同目录 `aggregate-design-V{NN}.md` | 落地后冻结 |
| ③ 读投影 | 本轮怎么查（读模型 + 读源） | 同目录 `projection-read-V{NN}.md` | 落地后冻结 |

- **三级结构**：需求目录（业务目标，人定）→ 聚合目录（一个聚合一个）→ 轮次（文件名 `-V{NN}`，各聚合独立递增）。
- **每轮固定三份**：不适用时薄写「本轮无变更 + 原因 + 见 `xxx-V{M}.md` §N」，不省略、不跳号。
- **落地即冻结**：代码落地后三份不再修改，只允许文字勘误与 ② §10.6 实施备注。
- **不生成实现代码**；代码交给 S4 / S5 / S6 / S3。

## 2. 场景模型

```text
需求 ──┬─ 首轮 ───► 勘察代码 → 聚合识别 → 语义（G1→G2 定稿）→ 写聚合 → 读投影 → 落地 → 核对 → 冻结
       └─ 后续轮 ──► 同需求加 V{N+1}（能推出）｜ 新建需求目录（推不出）
```

关键约束：

1. **一轮三份**：语义未定稿不得动 ②③；三份都要有（不适用就薄写）。
2. **语义必须人工确认**才能进入技术设计；未确认的语义视为草稿。
3. **取消点单**：不再问「要不要出写设计 / 要不要出投影」。
4. **上游优先**：②③ 发现要改业务意图，先回 ① 改并定稿，再逐级对齐；不在 ②③ 里打补丁。
5. **落地即冻结**：已落地的那份不得回改，设计要变开下一轮。
6. 存量项目先按 §4.1 勘察代码，再开 `V01` 写三件套。

## 3. 输入

- 业务需求文本 / 口述 / 现有代码。
- **项目前置条件清单**（必读，见 `bp.design-doc-prerequisites`）；清单不存在时先协助建立。
- 后续轮：代码勘察结果（含 commit 与核对日）+ 同目录上一轮三件套（作为基线）。

## 4. 工作流（一轮四阶段，10 步展开）

| 步 | 动作 | 产出 / 判定 |
| --- | --- | --- |
| 0 | **代码勘察 + 工作区准备 + 核前置条件 + 读判决名单** | 确认需求名与轮次号 → 调 `scripts/design-doc-workspace.sh new <需求> <agg...>`（或 `next-round`）建目录（同时预置 `aggregates/{agg}/`）；按 §4.1 清单勘察代码；核前置条件清单；**读 `docs/design/aggregates/{agg}/accepted.md`（不存在则跳过），命中的旧判决直接引用，不重开讨论** |
| 1 | 判定场景 | 新建 / 加聚合 / 改聚合 |
| 2 | 聚合识别 | 事件风暴四步：聚合候选、边界、不变量、粒度 |
| 3 | **G1 产出语义第 1 稿** | 新建：全量，基线写「无（新建）」；后续轮：按章标「重列 / 无变更，见 `semantics-V{M}.md` / 新增 / 废弃」，**与代码的差异就地标 `（当前：xxx）`**；头部写 `轮次：V0N ｜ 第 1 稿 ｜ 状态：草稿 ｜ 代码基线` |
| 4 | **G2 语义迭代 → 定稿** | 每稿只改用户点到的章节 + 连带章节，R / Q 只增不改；汇报三行（改了哪几章 / 新增哪些 R·Q·动作 / 附录 C 还剩什么）；用户显式说「定稿」才置「已确认」 |
| 5 | **出写聚合** | 产 11 节，§1.4 元素级追溯，**§7.1 落列形态决策（A 型需确认）**，§10.2 待回流登记 |
| 6 | **出读投影** | 产 6 节；本轮读侧不变则薄写「无变更 + 见 `projection-read-V{M}.md`」 |
| 7 | 一致性校验 + 各自检 | ① 的 R / 动作 / 事件 **⊆** ② §1.4；③ 的 Q **=** ① §8；③ 事件 **⊆** ② §5.1；③ 字段 **⊆** ② §7 |
| 8 | 交棒实施 | 三份状态均为「已确认」后，由 S4 / S5 / S6 / S3 落地 |
| 9 | **落地核对 → 冻结 → （交付后）追加判决与归档** | 按 `design-doc-template` §5.3 核三条（§8 改动清单逐行有实现 / §4.4 规则逐列一致 / ③ §6 查询族有实现）→ 只补 §10.6 实施备注 → 三份置「已落地」→ **本轮新确立且跨轮有效的判决追加进 `aggregates/{agg}/accepted.md`（无则不写，见 `bp/design-doc-accepted`）** → 需求交付后调 `archive <需求> --yes`（无 TTY 必带 `--yes`；④ **不随目录搬走**） |

**纯技术轮**：不再跳过语义，而是薄写——① 只写一节「本轮无业务语义变更 + 影响面」，② 头部写 `语义基线：semantics-V{M}.md（本轮无变化）`。

### 4.1 代码勘察清单（每轮开场固定动作）

每轮开场跑一遍，**不产出任何文档**。用于三处：迭代前摸清当前态、存量项目起步、用户问「现在实际是什么」。

| # | 观察目标 | 提取内容 | 需判断 |
| --- | --- | --- | --- |
| 1 | 聚合根 + 子实体 | 字段 / 充血方法 / `initData` / 构造期事件 | 否 |
| 2 | 枚举类 | 实际 code 值 | 否 |
| 3 | 操作注册表 / 规则注册表 | 操作码 / 消息码；注册表外的方法要对照 | 是 |
| 4 | 规则容器 `addRule` 的 lambda | 组 A/B/C / 激活条件 / **判定基准读 `old` 还是当前态** | **是** |
| 5 | DDL + Mapper | 表 / 索引 / 列形态（A 展开 / B JSON / search 生成列）/ TypeHandler | 是（不一致时以实际库为准） |
| 6 | 事件类 + 订阅登记 | 事件 / 载荷 / 构造方式 / 订阅方 | 否 |

硬规则：

- **勘察结果不进文档**：差异就地写进 ① 对应条目（`（当前：xxx）`），不另建现状文档。
- 第 4 项必须读 lambda 体——`addRule` 读 `old` 还是当前态，看签名看不出来。
- 发现代码缺陷：阻断级当场提出并登记待修，其余进 issue / `TODO`，不进设计文档。
- 用户问「现在实际是什么」时，按本清单读完直接回答，不产出文档。

### 4.2 回流（仅落地前）

唯一权威是模板 `design-doc-template` §3.1 回流矩阵，本处只给执行口径：

| 发现什么 | 处理 |
| --- | --- |
| 业务口径缺（规则 / 动作 / 字段 / 事件载荷 / 状态 / 查询场景 Q / 业务筛选口径） | **停手先改 ①**：① 出新稿 → 定稿（G2 重过）→ 回 ② 对齐 → 再回 ③；在 ② §10.2 记「已回 `semantics-V{M}.md`」 |
| 纯技术形态（表结构、索引、TypeHandler、读源、mapping、TTL、裁剪、分页） | 就地改 ② 或 ③，记 ② §10.1，不惊动 ① |

硬规则：

- **不跳级**：① 未定稿就改 ③，等于在流沙上盖房。
- **不一致要显性**：① 出新稿后 ②③ 置「待对齐」，在 ② §10.2 逐条列出未对齐项，不静默一致化。
- **止损**：本轮内 ≥ 3 稿仍在改语义，说明需求本身没定，停手回业务澄清。
- **落地后不再回流**：缺陷型问题改代码；设计要变则开下一轮 `V{N+1}`。

### 4.3 轮次判定（同目录加 V 还是新建需求目录）

默认：**能推出来就加后缀，推不出来就建新目录。** 三条全满足才加 `-V{N+1}`：

| # | 判据 |
| --- | --- |
| 1 | 业务目标相同：同一批业务对象、同一件事的延续 |
| 2 | 上一轮三件套就在同一目录，且能作基线（能引用具体章节） |
| 3 | 能写出「本轮替代上一轮什么」：哪几条 R / 哪个动作 / 哪个查询 |

硬规则：

- 任一含糊 → **新建需求目录**（保守默认）。
- **拿不准必须问用户，禁止自行择一**，问时给判断 + 推荐：

  > 这次的退款上限规则与上一轮同一批对象，能指明替代 `semantics-V01.md` §5 的 R3。我判断同目录开 `V02`。若你认为这是独立需求，我就新建目录。

## 6. 生成规则

- **只写设计，不写论证**：产出表 / 骨架 / DDL / mapping / 清单，不写取舍与推导。
- **单一事实源**：业务意图只在 ①；现状只看代码，不落文档；技术形态只在 ②③；已定的判决只在 ④（只增不改，不承接代码状态）。
- **编号稳定**：规则 R、查询 Q 跨文档不变，分配后不重排；轮次 `V{NN}` 是唯一对外编号。
- **条件子节不删、不重编号**：不适用时保留标题写「本聚合不适用：{原因}」，保证跳章引用稳定。
- **一轮三份**：不适用就薄写，不省略、不跳号；不再点单。
- **未定项集中**：框架签名、业务待确认、待回流项只在 ② §10；语义与读文档只引用。
- **落地即冻结**：只允许文字勘误与 ② §10.6 实施备注；设计要变开下一轮。
- **前置条件阻断**：未确认项对应的章节只写结构与占位，不写结论。
- **不设接口层章节**：端点与 Request / Response DTO 不在范围。

## 7. 防幻觉

- 框架符号以 `../kb/api-contract.md` 为唯一权威；未登记的一律进写文档 §10.4，不臆造签名。
- 边界 / 识别 / 演进判据以 KB 卡为权威；拿不准先 Read 对应卡。

## 8. 验收（13 条）

1. **三件套齐全**：同目录下 `semantics-V0N.md` / `aggregate-design-V0N.md` / `projection-read-V0N.md` 均存在；薄写的已在正文写清「无变更 + 原因 + 指向上一轮文件」。
2. **语义已人工确认**，头部有轮次、稿次、状态与代码基线，每章标了处理方式，有确认人与日期。
3. **三份均定稿后才交棒实施**；不存在语义未确认就已写技术设计。
4. **元素级追溯覆盖**全部动作、规则、事件、状态维度、依赖。
5. **一致性校验通过**：① 的 R / 动作 / 事件 ⊆ ② §1.4；③ 的 Q = ① §8；③ 事件 ⊆ ② §5.1；③ 字段 ⊆ ② §7。
6. **回流已清**：① 出新稿后 ②③ 不为「待对齐」，② §10.2 无「未回」。
7. **前置条件清单中相关项已确认**；未确认项对应章节只有结构与占位。
8. 写文档自检全通过（含组 C 读 old、差量顺序、执行器选型）。
9. 读文档自检全通过（含读源澄清、Q 编号对齐、直读有索引）。
10. 横切章节只在写文档出现，覆盖写 + 读。
11. **落地核对已过**：`design-doc-template` §5.3 三条通过（§8 改动清单逐行有实现 / §4.4 规则逐列一致 / ③ §6 查询族有实现）。
12. **已落地即冻结**：三份状态为「已落地」；§10.4 已回填；§10.6 只有实施备注、无「设计一套实施一套」；设计变更的开下一轮而非回改。
13. **判决名单已对账**：第 0 步已读 `accepted.md`（或确认不存在）；本轮若经用户拍板定了新判决则已追加（含作废行），无新判决则未写「无新增」；该文件未随 `archive` 搬走。
