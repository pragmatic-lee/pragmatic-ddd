# ddd-design-doc（聚合设计文档产出）

> 类型：设计文档产出能力
> 版本：v3.4 · 适用框架：2.1.0-SNAPSHOT
> 共享知识：`../kb/`（只读引用，见 `../kb/README.md`）
> 统一结构：`documentation/best-practices/design-doc-template.md`（三契约 + 一快照总说明）+ 四份模板

## 1. 定位

把「一份需求」转化为「三契约 + 一快照」，每份独立交付、独立评审：

| 文档 | 性质 | 产出 | 落盘 | 评审人 |
| --- | --- | --- | --- | --- |
| ① 本次需求语义 | 契约 | 本次需求的属性 / 动作 / 事件 / 规则 / 状态 / 依赖 / 查询场景 | `docs/design/changes/active/{需求}/{agg}/semantics.md` | 业务方 + 产品 |
| ② 聚合写 | 契约 | 写模型 + 关系表持久化 | `docs/design/changes/active/{需求}/{agg}/aggregate-design.md` | 开发 |
| ③ 投影读 | 契约 | 读模型 + 读源结构（ES / Redis / 数据库直读） | `docs/design/changes/active/{需求}/{agg}/projection-read.md` | 开发 |
| ④ 聚合事实 | **快照** | 从代码推导的当前态 + 未消除问题 | `docs/design/aggregates/{agg}/facts.md` | 开发 |

- ② 为主文档，统管横切（改动清单 / 测试 / 风险 / 实施回填）；③ 不设这三章。
- **①②③ 归档后沉入 `changes/archive/{需求}/`**；④ 永不归档，随代码持续更新。
- **不生成实现代码**；代码交给 S4 / S5 / S6 / S3。

## 2. 场景模型

```text
需求 ──┬─ ① 全新需求 ──► 聚合识别 → 语义（G1，多轮迭代）→ 定稿（G2）→ ②（G3 点单）→ ③（G4 点单）→ 实施 → 产 ④
       ├─ ② 迭代需求 ──┬─ 加聚合 ─► 聚合识别（新增）→ 同上
       │               └─ 改聚合 ─► 聚合演进（先改语义）→ 同上
       └─ ③ 现状型 ───► 读代码 → 产 / 更新 ④（存量建基线、实施后同步）
```

关键约束：

1. **一次只产一份**：① 未确认不得动 ②③；② 未定稿不得顺手开 ③。
2. **语义必须人工确认**才能进入设计阶段；未确认的语义视为草稿。
3. **②③ 是点单，不是默认全出**：用户没说要投影读设计就不写；不做时在 ① 或 ② 末尾写一句决定，不靠沉默。
4. **上游优先**：②③ 发现要改业务事实，先回 ① 改并定稿，再逐级对齐；不在 ②③ 里打补丁。
5. **④ 未更新不得进入下一次迭代**；它是下一轮需求的唯一基线。
6. 存量项目先走 ③ 建 ④，再按 ② 开始迭代。

## 3. 输入

- 业务需求文本 / 口述 / 现有代码。
- **项目前置条件清单**（必读，见 `bp.design-doc-prerequisites`）；清单不存在时先协助建立。
- 迭代场景：④ `aggregates/{agg}/facts.md`（基线）+ `changes/archive/` 中该聚合最近一次契约（用于「替代上一版哪些章节」标注）。

## 4. 工作流（闸门制，10 步）

**一次只产一份**：① 未确认不得动 ②③；② 未定稿不得顺手开 ③。②③ 按 G3 / G4 点单产出，未点名不写。

| 步 | 动作 | 产出 / 判定 |
| --- | --- | --- |
| 0 | **工作区准备 + 核前置条件 + 读 ④** | 确认需求名（`{YYYYMM}-{slug}` 或需求编号）→ 调 `scripts/design-doc-workspace.sh new <需求> <agg...>` 建目录；读对应聚合的 ④；核前置条件清单 |
| 1 | 判定场景 | 新建 / 加聚合 / 改聚合 |
| 2 | 聚合识别 | 事件风暴四步：聚合候选、边界、不变量、粒度 |
| 3 | **G1 产出语义第 1 轮** | 新建：全量，基线与「无（新建）」；迭代：按章标「重列 / 无变更，见基线 / 新增 / 废弃」，**与事实的差异就地标注 `（当前：xxx）`**；头部写 `版本：v1 ｜ 状态：草稿` |
| 4 | **G2 语义迭代 N 轮 → 定稿** | 每轮只改用户点到的章节 + 连带章节，R / Q 只增不改；汇报三行（改了哪几章 / 新增哪些 R·Q·动作 / 附录 C 还剩什么）；用户显式说「定稿」才置「已确认」 |
| 5 | **G3 写设计（需用户点单）** | 先问「现在要出写设计吗」；确认后产 11 节，§1.4 元素级追溯，§10.2 待回流登记 |
| 6 | **G4 投影读设计（需用户点单）** | 先问「查询场景要落成投影吗」；② 定稿后才开，产 6 节；不做时把决定写进 ① 或 ② 末尾 |
| 7 | 一致性校验 + 各自检 | ① 的 R / 动作 / 事件 **⊆** ② §1.4；③ 的 Q **=** ① §8；③ 事件 **⊆** ② §5.1；③ 字段 **⊆** ② §7 |
| 8 | 交棒实施 | 各份状态均为「已确认」后，由 S4 / S5 / S6 / S3 落地 |
| 9 | **回填 + 更新 ④ + 归档** | 填 §10.6 → 覆盖更新涉及的每个 `aggregates/{agg}/facts.md` → 调 `scripts/design-doc-workspace.sh archive <需求>` |

**纯技术改动**（索引、日志、类型调整、性能优化等无语义变更）可跳过第 3–4 步（G1 / G2）：在 ② §1.5 标「纯技术，无语义变更」，并在 §10.1 写清无业务影响；目录下只有 ②（必要时加 ③）。

### 4.1 现状型分支（读代码 → ④）

用于三处：存量项目建基线、每次实施后更新 ④、用户问「现在实际是什么」。

按 `bp.design-doc-facts` §5 的提取顺序执行，不另创一套：

| 步 | 动作 | 产出 |
| --- | --- | --- |
| 1 | 定位代码：聚合根、子实体、枚举、注册表、规则容器、DDL、Mapper、事件类、订阅登记 | 待读清单 |
| 2 | 机械提取（不做评价） | ④ §3 八个子节 |
| 3 | 对照 DDL 与 Mapper；不一致时以实际库为准 | §3.4 差异标注 |
| 4 | 找出代码侧未修问题（不看语义） | ④ §4 未消除问题 |
| 5 | 分类：接受的现状 / 已移交语义文档 | ④ §4 表后两段 |
| 6 | 填 §2 依据与 §5 变更记录 | ④ 完整 |

硬规则：

- **④ 只写代码事实**，不写「应该」、不写设计理由。
- ④ 不写「语义 vs 实现」的完整比对——那类差异就地写在语义文档对应条目上；②§4 只保留未修问题摘要。
- 第 2 步不做判断，第 4—5 步才需要人。
- 更新 ④ 时覆盖写，不新增历史版本；历史看 §5 变更记录。

### 4.2 回流（下游发现上游缺东西）

唯一权威是模板 `design-doc-template` §3.1 回流矩阵，本处只给执行口径：

| 发现什么 | 处理 |
| --- | --- |
| 业务口径缺（规则 / 动作 / 字段 / 事件载荷 / 状态 / 查询场景 Q / 业务筛选口径） | **停手先改 ①**：① 升版 → 定稿（G2 重过）→ 回 ② 对齐（G3 重过）→ 再回 ③；在 ② §10.2 记「已回 ① vN」 |
| 纯技术形态（表结构、索引、TypeHandler、读源、mapping、TTL、裁剪、分页） | 就地改 ② 或 ③，记 ② §10.1，不惊动 ① |

硬规则：

- **不跳级**：① 未定稿就改 ③，等于在流沙上盖房。
- **不一致要显性**：① 升版后 ②③ 置「待对齐」，在 ② §10.2 逐条列出未对齐项，不静默一致化。
- **止损**：① 升版 ≥ 3 次说明需求本身没定，停手回业务澄清。
- **归档后不回改 ①**：发现遗漏开新需求目录写增量语义。

## 6. 生成规则

- **只写设计，不写论证**：产出表 / 骨架 / DDL / mapping / 清单，不写取舍与推导。
- **单一事实源**：业务事实只在语义文档定义；设计文档引用编号，不重抄。
- **编号稳定**：规则 R、查询 Q 跨文档不变，分配后不重排。
- **条件子节不删、不重编号**：不适用时保留标题写「本聚合不适用：{原因}」，保证跳章引用稳定。
- **一次一份**：默认只产出一份文档正文；②③ 需用户点名，未点名先问不先写。
- **未定项集中**：框架签名、业务待确认、待回流项只在写文档 §10；语义与读文档只引用。
- **前置条件阻断**：未确认项对应的章节只写结构与占位，不写结论。
- **不设接口层章节**：端点与 Request / Response DTO 不在范围。

## 7. 防幻觉

- 框架符号以 `../kb/api-contract.md` 为唯一权威；未登记的一律进写文档 §10.4，不臆造签名。
- 边界 / 识别 / 演进判据以 KB 卡为权威；拿不准先 Read 对应卡。
- KB 是产物不是源：源约定变更先回写 `documentation/best-practices/` 再重派生。

## 8. 验收（12 条）

1. 按本次闸门实际产出的文档齐全，同在一个需求目录（`changes/active/{需求}/{agg}/`）；未产出 ② 或 ③ 时，① 或 ② 末尾有一句用户决定记录（不做 / 走直读 / 另行安排）；④ 在 `aggregates/{agg}/`。
2. **语义文档已人工确认**，头部有版本、状态与基线，每章标了处理方式，有确认人与日期。
3. **一次只产一份未破**：不存在 ① 未确认就已写 ②，或 ② 未定稿就已写 ③。
4. **元素级追溯覆盖**全部动作、规则、事件、状态维度、依赖。
5. **一致性校验通过**：① 的 R / 动作 / 事件 ⊆ ② §1.4；③ 的 Q = ① §8；③ 事件 ⊆ ② §5.1；③ 字段 ⊆ ② §7。
6. **回流已清**：① 升版后 ②③ 不为「待对齐」，② §10.2 无「未回」。
7. **前置条件清单中相关项已确认**；未确认项对应章节只有结构与占位。
8. 写文档自检全通过（含组 C 读 old、差量顺序、执行器选型）。
9. 读文档自检全通过（含读源澄清、Q 编号对齐、直读有索引）。
10. 横切章节只在写文档出现，覆盖写 + 读。
11. **④ 已更新**：§3 实际结构与代码一致；§4 未消除问题已刷新（修掉的已删行）。
12. **归档前 §10.4 与 §10.6 回填完成**，①②③ 归档且 ④ 未归档。
