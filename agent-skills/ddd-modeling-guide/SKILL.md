# ddd-modeling-guide（聚合建模引导，P2）

> 类型：P2（建模引导，长线）
> 版本：v2.0 · 适用框架：2.1.0-SNAPSHOT
> 共享知识：`../kb/`（只读引用，见 `../kb/README.md`）
> 关联：`../kb/bp/aggregate-design.md` · `../kb/bp/aggregate-database-design.md` · `../kb/bp/entity-design.md`

## 1. 定位

帮助用户**把业务概念落地为正确的 DDD 聚合边界与聚合度**。这是一个多轮引导 + 决策记录过程，**不生成代码**；结论形成后交给 S2/S4 落地。

## 2. 输入

- 业务背景描述（用户口述 / 现有代码 / 需求文档）。
- 可选：已识别的命令、事件、领域概念清单。

## 3. 工作流（多轮问答 + 收敛）

### 步骤 1：事件风暴（识别候选）

- 引导用户列出业务发生的**事件**（过去式）：「订单已支付」「库存已扣减」……。
- 每个事件归属一个潜在聚合；事件密集、强一致的动作归同一聚合候选。
- 参考：`kb/bp/event-modeling.md`（事件命名 / 事实语义）。

### 步骤 2：提炼不变性（边界判据）

- 对每个候选聚合问：「哪些业务规则必须在**一次事务内**保持一致？」
- 强一致不变性 → 同一聚合内；最终一致 → 跨聚合走事件（见 `aggregate-design.md` 小聚合原则）。
- 示例：订单总额 = Σ 订单项金额 → 同聚合；订单支付成功 → 扣库存 → 跨聚合（事件）。

### 步骤 3：判定聚合度（该大该小）

- 用「小聚合」原则校验：聚合是否只承载真正需要强一致的成员？
- 判据清单：
  - 是否引入了不需要一起锁的实体？（是 → 拆出）
  - 跨聚合是否只持 ID？（见 `hard-constraints.md` 约束 13）
  - 子实体是否随父聚合存在、无独立访问？（是 → 同聚合子表；否 → 独立聚合）
- 参考：`kb/bp/aggregate-database-design.md` §2（一表/多表判定）、`entity-design.md`（实体 vs 值对象）。

### 步骤 4：引用方式决策

- 跨聚合：只持 ID 引用（约束 13），不持对象。
- 聚合内子实体：`TrackedList` + 独立子表；无身份值对象：并入父表 JSON。

### 步骤 5：产出建模决策表

- 用 `templates/modeling-worksheet.md` 记录：聚合清单 / 成员 / 不变性 / 事务边界 / 跨聚合交互 / 表设计。
- 交付结论给用户，并指向 S2/S4 落地。

## 4. 生成规则

- 多轮收敛：每轮只推进一个决策点，不在信息不足时下结论。
- 引导而非替用户拍板：给出「推荐 + 理由 + 风险」，让用户决策。
- 不生成代码；结论经用户确认后交给 S4。

## 5. 常见误判

| 误判 | 纠偏 |
| --- | --- |
| 一个聚合包下整个领域 | 小聚合；按不变性切分 |
| 跨聚合持对象引用 | 只持 ID（约束 13） |
| 把最终一致当强一致 | 跨聚合走领域事件 |
| 无身份值对象建子表 | 并入父表 JSON |
| 子实体被他聚合独立访问却塞同聚合 | 提为独立聚合 |

## 6. 防幻觉

- 边界/聚合度判据以 `aggregate-design.md` / `aggregate-database-design.md` / `entity-design.md` / `hard-constraints.md` 为准。

## 7. 验收

- 产出 `modeling-worksheet.md` 决策表，字段完整。
- 结论与「小聚合 / 跨聚合只持 ID / 表边界=聚合边界」原则一致。
- 用户确认后可由 S4 落地，无返工。
