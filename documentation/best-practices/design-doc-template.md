# 聚合设计文档标准（含模板）

> 本文档是 **使用 Pragmatic DDD 框架的团队 / 开发者** 在 **新建一个聚合** 或 **修改一个既有聚合的实现** 时，应当遵循的**设计文档标准**。
>
> 目标：让不同团队、不同人产出的聚合设计文档**规格一致**——结构固定、章节命名统一、内容要求明确——使评审者与实现者（无论是人还是 AI 辅助工具）都能以相同方式阅读、比对与落地，而不是「一千个人一千种写法」。
>
> 本文只定义「**文档应该长什么样**」，不讲解框架机制本身；涉及框架能力（规则、事件、仓储等）时只给出对应最佳实践文档的链接。

## 1. 标准定位与适用范围

### 1.1 什么是聚合设计文档

聚合设计文档描述「**一个聚合如何被设计与实现**」：它的边界、内部模型、状态与行为、业务规则、领域事件、持久化方式，以及（修改场景）具体改动哪些文件。它是实现前的**唯一输入**与**评审依据**。

### 1.2 何时产出

| 场景 | 是否产出 | 差异 |
| --- | --- | --- |
| 新建一个聚合 | 是 | 以「静态模型 + 行为 + 规则 + 事件 + 持久化」为主 |
| 修改既有聚合实现 | 是 | 额外包含**根因分析**与**改动清单 / 落地顺序** |

### 1.3 为什么需要统一标准

- **可评审**：评审者无需先猜文档结构，直接定位到「边界」「规则」「事件」等固定章节。
- **可交接**：接手者按相同结构即可读懂任意聚合的设计意图。
- **可落地**：实现者（人或 AI 辅助）按固定章节与「改动清单」可获得确切、无歧义的输入，减少猜测。
- **可比对**：同一标准下，多个聚合的设计文档可以直接横向比对一致性。

### 1.4 与相关文档的区别

| 文档类型 | 回答什么 | 稳定性 / 位置 |
| --- | --- | --- |
| 框架最佳实践（如规则范式、事件建模） | 框架能力**怎么用** | 长期稳定，沉淀复用 |
| 聚合设计文档（本文标准的产出物） | 这个聚合**怎么设计 / 改** | 一次性，随需求迭代 |
| 框架核心机制文档 | 框架底层**机制是什么** | 随版本演进 |

设计文档**不重复讲解框架机制**，只引用对应最佳实践文档的链接。

### 1.5 命名与存放建议

按团队约定存放即可；建议命名为 `{聚合名}-{动作}-design.md`，例如 `order-ship-and-logistics-correction-design.md`、`customer-aggregate-design.md`。本文不强制存放路径，仅约束**文档内部结构**。

## 2. 文档结构（固定骨架）

每份聚合设计文档由以下 **13 节**组成，章节编号与标题**必须保持一致**，以便跨文档定位与自动化抽取。

| # | 章节 | 必选 | 回答的问题 |
| --- | --- | --- | --- |
| 1 | 概述与背景 | ✅ | 设计 / 修改哪个聚合，为什么，范围多大 |
| 2 | 聚合边界与职责 | ✅ | 聚合根是谁，包含哪些实体 / 值对象，不变量是什么 |
| 3 | 领域模型静态结构 | ✅ | 类 / 字段 / 标识符 / 值对象长什么样 |
| 4 | 状态与行为设计 | ✅ | 有哪些操作 / 命令，状态机与允许矩阵 |
| 5 | 业务规则设计 | ✅ | 不变量如何表达，何时校验（当前态 / 旧快照） |
| 6 | 领域事件设计 | 视场景 | 发出哪些事件，载荷、订阅者、投影影响 |
| 7 | 持久化与仓储设计 | ✅ | 表结构、映射、仓储接口、投影 |
| 8 | 应用层设计 | 视场景 | Input、命令处理、WriteService 入口 |
| 9 | 接口层设计 | 视场景 | HTTP / RPC 入口、Request / DTO |
| 10 | 时序 | ✅ | 一次调用的完整执行路径 |
| 11 | 改动清单与落地顺序 | ✅ | 新建 / 改动哪些文件，按什么顺序 |
| 12 | 测试清单 | ✅ | 怎么验证设计被正确实现 |
| 13 | 风险与待确认事项 | ✅ | 有什么坑，什么没定 |

> **规则**：第 6 / 8 / 9 节按场景选填；**其余 10 节恒必选**。某节确实不适用时，**保留标题并写明「本次不适用，原因：……」**，不要删除——删节会让读者 / 工具误判为遗漏。

## 3. 各节内容规则

### 3.1 结论先行（文档最顶部）

正文之前用引用块给出**一句话结论**，包含「**选什么方案 / 怎么设计**」与「**为什么**」。评审者只看这一句即可判断方向。

```markdown
> 结论先行：**订单聚合拆分为「发货」与「修正物流」两个独立操作**。
> 理由：二者职责冲突，合并实现导致重复执行时状态被错误推进。
>
> 本文仅为设计文档，未改动任何代码。
```

### 3.2 概述与背景

- **新建聚合**：说明业务诉求、聚合要解决的核心问题、影响范围。
- **修改聚合**：必须包含**根因分析**，建议三层递进——

| 层级 | 问什么 |
| --- | --- |
| 直接原因 | 哪段实现没拦住 / 没覆盖 |
| 深层原因 | 为什么没拦住（执行顺序 / 模型漏洞） |
| 本质原因 | 为什么会有这样的设计（职责 / 边界 / 模型层面） |

涉及代码引用的，统一用 `` `行号:相对路径` `` 格式并给出可点击跳转；本质原因必须落到职责 / 边界 / 模型层面，而非「忘了写判断」。

### 3.3 聚合边界与职责

明确：

- 聚合根（Aggregate Root）是谁，为什么是它。
- 聚合内包含哪些实体、值对象，哪些**不属于**本聚合（应引用 / 另立聚合）。
- 聚合维护的核心不变量（Invariant）。

> 明确「不归本聚合管什么」与「管什么」同等重要，防止边界蔓延。

### 3.4 领域模型静态结构

给出聚合内类的**可直接编译**的骨架代码（含完整包名 / 导入 / 构造签名）：

| 元素 | 写什么 |
| --- | --- |
| 聚合根 | 类定义、标识符、持有的实体 / 值对象集合 |
| 值对象 | 不可变性、校验、相等语义 |
| 标识符 | ID 类型（如 `OrderId`） |
| 枚举 | 出入参与投影中的枚举值处理（见下方约束） |

约束（框架约定）：出入参 / 查询条件 / 应用层 Input 中的枚举值统一用 `Integer` / 字符串等基础类型承载；投影读模型中的枚举同样转为基础类型，不再使用枚举类型本身。详见《枚举值处理约定》。

### 3.5 状态与行为设计（含允许矩阵）

- 列出聚合支持的**操作 / 命令**及其语义。
- 状态类需求用**矩阵表**穷举「什么状态允许什么操作」，避免遗漏组合：

| 旧状态 | 操作 A | 操作 B |
| --- | --- | --- |
| `PENDING` | ✅ 放行 | ❌ 拒绝（未发生，谈不上修正） |

- 显式写出**边界澄清**：哪些场景**不属于**本设计（明确「不做什么」与「做什么」同等重要）。

### 3.6 业务规则设计（框架最高频坑）

凡「判断状态是否被推进过」的前置类规则，必须明确判定依据：

| 判定场景 | 读谁 | 原因 |
| --- | --- | --- |
| 字段值不变量（金额为正、客户非空） | 当前态 | 与执行顺序无关 |
| 状态前置条件（仅待发货可发货） | **旧快照** `old` | 框架 `execute` 先跑领域逻辑后校验，当前态已被改 |

必须写出规则的激活条件（如基于 `hasOperation`）与新旧读法的对应关系。详见《聚合业务规则（OrderRule 范式）》。

### 3.7 领域事件设计

| 事件 | 携带内容 | 订阅者 | 投影影响 |
| --- | --- | --- | --- |

说明事件触发时机、载荷（改前 / 改后等），以及被哪些投影 / 下游消费。

### 3.8 持久化与仓储设计

| 层 | 写什么 |
| --- | --- |
| 表结构 | DDL、字段、索引 |
| 映射 | Mapper / ORM 映射关系 |
| 仓储 | 仓储接口与实现要点 |
| 投影 | 受影响读模型，即使无改动也要写「零改动，理由：……」 |

### 3.9 应用层 / 接口层设计

- **应用层**：Input、Updater、WriteService 入口与调用顺序。
- **接口层**：HTTP / RPC 方法、路径、Request / Response DTO 是否变更。
- 即便零改动，保留标题并说明理由，避免被误判为遗漏。

### 3.10 时序

用文字或序列描述一次调用的完整执行路径，重点标注**调用顺序约束**（为什么不能换顺序），例如：必须先暂存改前值再赋值，否则拿不到 before / after。

### 3.11 改动清单与落地顺序

用表格给出**确切文件路径 + 动作（新增 / 改 / 删）+ 说明**，三列缺一不可：

| # | 文件 | 动作 | 说明 |
| --- | --- | --- | --- |
| 1 | `domain/.../operation/OrderOperationRegistry.java` | 改 | 新增 `CORRECT_LOGISTICS` |
| 2 | `domain/.../event/OrderLogisticsCorrectedEvent.java` | 新增 | 携带改前 / 改后 + 原因 |

并单独给出**落地顺序**，保证每一步都可编译、可单测：

> 建议顺序：`1→4→5→3→2→…`：先立规则与操作码，再改聚合，最后接应用层与接口层。

### 3.12 测试清单

| # | 用例 | 期望 |
| --- | --- | --- |
| T2 | **已发货订单再次发货（核心）** | 拒绝，`ORDER_SHIP_STATUS_INVALID`，DB 不变、不发布事件 |

- 期望写**确切的消息码常量名 / 状态枚举值**，不写「报错」。
- 标注哪几条是**验收核心**（如「T2 / T7 是本次验收核心」）。
- 区分规则层单测与应用服务集成测。

### 3.13 风险与待确认事项

| # | 事项 | 说明 | 建议 |
| --- | --- | --- | --- |

风险表给**触发条件与应对**；顺带发现的同类缺口一律记入并标注「不在本次范围」，用于另开文档，避免范围蔓延。

## 5. 标准符合性自检清单

文档产出后逐项自检，**任一项不满足即不符合本标准**：

| # | 检查项 | 不满足的后果 |
| --- | --- | --- |
| 1 | 顶部有结论先行块（含「结论 + 为什么」） | 评审方向不明 |
| 2 | 修改类含根因分析（建议三层） | 只修表象，同类缺陷复发 |
| 3 | 聚合边界与职责明确，含「不归本聚合管」 | 边界蔓延 |
| 4 | 静态结构给出可直接编译的骨架（真实类名 / 构造） | 实现者无法落地 |
| 5 | 状态类需求含允许矩阵或等价穷举表 | 遗漏状态组合 |
| 6 | 明确写出「不属于本设计」的边界 | 范围失控 |
| 7 | 前置类规则明确标注读旧快照 | 规则写对但拦不住 |
| 8 | 持久化 / 应用 / 接口层齐全，零改动写明理由 | 误判为遗漏 |
| 9 | 改动清单含确切文件路径 + 动作 + 说明 | 找不到文件 |
| 10 | 给出落地顺序且每步可编译 | 中途编译失败 |
| 11 | 测试清单含确切消息码 / 枚举值，标出验收核心 | 无法判断实现正确 |
| 12 | 风险含触发条件与应对，缺口标注「不在本次范围」 | 踩坑且范围失控 |
| 13 | 章节编号与标题与本标准一致（固定 13 节） | 文档规格不统一 |

## 6. 常见反模式

| 反模式 | 问题 | 正确做法 |
| --- | --- | --- |
| 只有方案没有根因（修改类） | 可能没对症，同类缺陷反复出现 | 写三层根因，本质原因落到职责 / 边界 |
| 聚合边界不清、什么都往里塞 | 聚合膨胀、并发冲突 | 明确「不归本聚合管」 |
| 代码引用不带路径行号 | 评审与实现者都无法定位 | 统一 `行号:相对路径` 格式 |
| 只在正文描述改动无清单表 | 易漏改 / 改错 | 独立改动清单表 + 落地顺序 |
| 期望写成「报错 / 失败」 | 无法断言，测试形同虚设 | 写确切消息码常量名与状态枚举值 |
| 状态前置规则读当前态 | 规则永远通过，缺陷依旧 | 前置判断必须读 `old` |
| 基础设施层直接省略 | 误判遗漏或真漏建表 / 改投影 | 保留标题写「零改动，理由：……」 |
| 顺手一起改顺带发现的缺陷 | 范围蔓延，评审与回滚困难 | 记入风险表，标注「不在本次范围」 |
| 文档里重复讲解框架机制 | 冗长且双份维护 | 只给最佳实践链接 |

## 附：框架机制参考

设计文档只引用、不重复框架机制。相关能力详见：

- 聚合业务规则（OrderRule 范式）：规则容器、激活条件与旧快照判定
- 应用层落地模式：`execute` 模板与「先领域逻辑后校验」执行顺序
- 操作注册表设计：新增操作时操作码的声明方式
- 事件建模指南：新增领域事件的写法
- 枚举值处理约定：出入参与投影中枚举值的基础类型承载
- 仓储设计 / 投影设计：持久化与读模型的实现要点
- 核心：业务规则引擎：`EntityRule` / `RuleCheckResult` 底层契约
