# 聚合设计文档标准（两份 · 总说明与索引）

> 本文是 **ddd-design-doc** 能力产出设计文档的**总说明与索引**。
> 原「单一 13 节文档」已演进为**两份独立文档**（写 / 读），对应 CQRS 的写模型与读模型两个关注点；存储设计不再单独成篇，按归属并入两份。本文只定义**通用规则与两份的协同关系**，具体骨架见两份模板。

## 1. 为什么是两份

一个聚合的设计天然分成两个关注点，且各自的存储设计应与所服务的模型同处一篇：

- **聚合写（写模型）**：聚合根、实体 / 值对象、状态机、业务规则、领域事件——命令如何改变聚合；以及其**关系表持久化**（表结构 / 映射 / 仓储）。
- **投影读（读模型）**：异构存储副本怎么建、怎么查——与写模型装配解耦的独立读视图；以及其**投影持久化**（ES 索引 / Redis 结构）。

存储设计此前单独成篇（持久化文档），导致关系表与写模型割裂、ES / Redis 副本与读模型割裂，评审时需跨三份拼装。现按归属归位：关系表进写文档，ES / Redis 副本进读文档。

两份各自成篇，便于分头评审、独立落地。

## 2. 两份文档与定位

| 文档 | 定位 | 落盘命名（同一需求共用 `v{N}`） | 统管横切？ |
| --- | --- | --- | --- |
| **① 聚合写**（主文档） | 写模型设计 + 关系表持久化 | `docs/design/{聚合名}-aggregate-design-v{N}.md` | ✅ 统管整体（改动清单 / 测试 / 风险） |
| **② 投影读**（专项） | 读模型设计 + 投影持久化（ES / Redis） | `docs/design/{聚合名}-projection-read-design-v{N}.md` | ❌ 只聚焦自身 |

> 不再产出 `docs/design/{聚合名}-persistence-design-v{N}.md`：存储设计已并入上述两份。

## 3. 通用规则（两份共用）

- **结论先行**：每份文档顶部引用块给出「选什么方案 + 为什么」；附「本文仅为设计文档，未改动任何代码」。
- **版本化**：同一需求的两份文档共用同一 `v{N}`；文件名与结论先行块均含版本。
- **枚举基础类型**：出入参 / 查询条件 / 应用层 Input 的枚举用 `Integer` / 字符串；投影读模型枚举同样转为基础类型（见 [`enum-value`](/best-practices/enum-value)）。
- **防幻觉红线**：边界 / 识别 / 演进判据以 KB 卡与模板为权威；拿不准先 Read 对应卡，缺符号向用户提问；KB 是产物不是源，源约定变更先回写 `documentation/best-practices/` 再重派生。
- **横切统管**：改动清单 / 测试 / 风险**只在聚合写文档**出现，且覆盖**整体需求**（写 + 读，含各自的存储落地），一份主文档驱动整体落地。写路径的执行顺序在写文档应用层设计章节体现，**不再单列「时序」章节**。
- **各自独立成篇**：两份不强关联、不强制交叉引用（写文档事件表的「投影影响」列仍写事实，但不强链读文档）。
- **不适用节保留标题**：某节确实不适用时保留标题并写明「本次不适用，原因：……」，不删节。

## 6. 符合性自检（总览）

- 两份文档各通过其对应模板的自检清单（写 12 项 / 读 7 项）。
- 两份版本号一致，且各自带结论先行块。
- 横切章节（改动清单 / 测试 / 风险）仅在写文档出现，覆盖整体需求。
- 存储设计归位：写文档含关系表设计、读文档含 ES / Redis 副本设计。
